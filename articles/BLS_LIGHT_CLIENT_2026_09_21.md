# JunoClaw's BLS Light Client: Trusting a Whole Chain With One Pairing Check

*How a sovereign Rust chain with BLS12-381 threshold consensus opens itself to the IBC universe — no bridge multisig, no counterparty upgrade, one pairing per block.*

---

## TL;DR

- **Bridges trust committees. Light clients trust math.** JunoClaw's consensus already produces one aggregated BLS12-381 signature per block — so a light client for our chain verifies **one pairing check**, not N validator signatures.
- **It's built.** A CosmWasm contract implementing the exact `08-wasm` light client interface `ibc-go` drives — `update_state`, `update_state_on_misbehaviour`, `status`, and more — with the wire format validated field-by-field against ibc-go's own contract API.
- **It's tested against the real thing.** 14/14 tests, including certificates generated by the same `blst`-backed DKG code our production nodes run.
- **It deploys without asking permission.** Any chain running 08-wasm (Osmosis, Juno, uni-7 testnet) can host it as a governance-voted client — no chain upgrade, no custom module.
- **What's left:** the relayer that ships headers to the counterparty, and the Merkle layout for packet-commitment proofs. Then ujclaw is tradable on Osmosis.

## The Problem With Bridges

Every cross-chain system answers one question: *who says the other chain's state is what it claims to be?*

Bridges answer: *a committee.* Five-of-nine multisig validators copying state both directions. It's fast to ship and simple to reason about — until the committee is compromised, the upgrade key leaks, or the oracle feed lies. Billions of dollars have exited through that door.

Light clients answer: *the chain itself.* The counterparty chain verifies the source chain's consensus signatures — actual finality proofs — before accepting any cross-chain message. A forged header requires forging consensus.

For most chains that's expensive: Tendermint light client verification checks a quorum of signatures and tracks validator-set changes across epochs — the largest bug surface in the history of IBC light clients.

JunoClaw made a different choice at genesis. It costs us nothing at verification time.

## The Insight: Consensus Already Signs the Block

JunoClaw runs Commonware simplex with BLS12-381 threshold signatures (`MinSig` variant). The validator set is fixed at genesis via a DKG ceremony — a single group public key in G2 (96 bytes), with no per-epoch validator-set churn.

When a block finalizes, the validators' individual signature shares aggregate into **one 48-byte signature** that could only have been produced by at least `2f+1` of the group. That signature *is* the finality certificate.

So the light client doesn't need:

- per-validator signature iteration
- validator-set diffs or trusting-period drift
- fork-choice heuristics

It needs exactly:

```
pairing(certificate, G2_generator) == pairing(hash_to_curve(proposal), group_public_key)
```

If that holds, ≥ `2f+1` of JunoClaw's stake signed that block. Equivocation — two valid certificates for conflicting payloads in the same round — is itself cryptographic proof that ≥ `f+1` shares were compromised, and the client freezes on sight.

One pairing. One hash-to-curve. That's the entire trust model for a whole chain.

## The Header Is Two Blobs and Two Numbers

The relayer's job is deliberately boring. For each finalized height, the JunoClaw node already persists:

- **`proposal_bytes`** — the consensus-encoded proposal (round, parent, payload digest)
- **`certificate_bytes`** — the raw 48-byte threshold signature

The light client header is those two blobs passed through verbatim, plus height and a nanosecond timestamp. No re-encoding, no transformation. A relayer is a courier that can't lie — every field it carries is either verified or rejected.

## Speaking Native IBC: The 08-wasm Contract

Verifying a pairing is only half the problem. The other half is being *drivable by ibc-go* — the module that runs on Osmosis, Juno, and most of the Cosmos ecosystem.

That's what `08-wasm` is for: a generic light client that delegates all client logic to a CosmWasm contract. The counterparty chain calls the contract's `sudo` and `query` entrypoints and treats it as any other client. Union proved the pattern with their cometbls client.

So we built the contract to ibc-go's exact contract ABI — field names, JSON tags, and response shapes taken from ibc-go's `contract_api.go` (verified against ibc-go main, API-compatible with v8.3+ through v11):

| Call | What it does | Status |
|---|---|---|
| `update_state` | Verify certificate, check monotonicity + equivocation, store consensus state, return updated heights | ✅ |
| `update_state_on_misbehaviour` | Two valid certs that conflict → freeze the client | ✅ |
| `status` | `Active` / `Frozen` | ✅ |
| `timestamp_at_height` | Packet-timeout support | ✅ |
| `verify_client_message` | Trustless dry-run of a header before submitting | ✅ |
| `check_for_misbehaviour` | Relayer misbehaviour detection | ✅ |
| `verify_membership` / `verify_non_membership` | Packet-commitment proofs — blocked on Merkle layout, returns an explicit error | ⏳ |

The details that bite people are handled: IBC `Height` revision semantics, base64 `[]byte` fields under Go's `encoding/json`, nanosecond timestamps, idempotent header replays, and headers that conflict with stored state rejected as misbehaviour rather than silently overwriting.

The contract builds to a ~708 KB wasm blob and needs **no BLS host function on the counterparty chain** — verification uses a pure-Rust BLS12-381 implementation inside the contract. That's why it runs anywhere CosmWasm runs.

## Tested Against the Real Thing

Unit tests with toy keys prove nothing. Our tests generate real DKG sharings and aggregate real threshold signatures using the same `blst`-backed Commonware code our production validators run — then verify those certificates with the contract's pure-Rust verifier.

The signing implementation and the verifying implementation share zero code. If they agree, the wire format and the math are right. If they ever disagree, that's a consensus fork waiting to happen — which is exactly what you want to find in a test, not on mainnet.

The same cross-implementation check caught a subtler thing along the way: a toolchain-level linkage bug (newer `rust-lld` stopped mapping bare `extern "C"` blocks to `env`-module imports, breaking *every* CosmWasm contract build on modern Rust — ours and the ecosystem's). One line in our VM fork restores the explicit import module, matching what the VM registers and what other ecosystems did for the same change. Sovereignty means you can fix the toolchain instead of waiting for it.

## What This Unlocks

**IBC to Osmosis, no permission required.** Deploying the client on Osmosis is a governance vote to allow the code ID — not a chain upgrade. Then: `ujclaw` escrowed on JunoClaw, `ibc/.../ujclaw` tradable on the largest Cosmos DEX. Fixed supply, 54.66M units, finally priced by an open market.

**The same primitive beyond Cosmos.** The verification core is one pairing — which maps directly onto:

- **EVM chains** (Avalanche, Ethereum L2s) via the EIP-2537 BLS12-381 precompile
- **Solana** via BLS syscalls in a native program
- **Off-chain** in any Rust or TypeScript verifier that needs to check a JunoClaw header — robots checking their own chain, agents verifying settlement

Every deployment anchors to the same root of trust: the genesis group public key.

## What's Left (Honestly)

1. **The relayer** — fetch `proposal` + `certificate` by height from the JunoClaw node API, wrap in the header format, submit `update_state`. Mostly plumbing.
2. **Membership proofs** — the block payload commitment needs to expose a Merkle root over IBC packet commitments so `verify_membership` can prove "this packet was committed at height H". Layout is designed; implementation is next.
3. **A testnet client first** — uni-7 (Juno testnet) or Osmosis testnet, one governance proposal, first verified header. Then mainnet.

Light clients are the safest interoperability primitive we know how to build. This one happens to also be the cheapest to verify — because the chain it trusts was designed to make trust cheap.
