## The Problem (30-Second Version)

A robot is making decisions 1000 times per second. Who checks that those decisions are safe? Today: nobody. The robot's own software says "I'm fine" and we trust it. If something goes wrong, we find out after the accident.

JunoClaw fixes this. Every batch of robot decisions gets:
1. A **mathematical proof** that safety rules were followed (like a receipt you can't fake)
2. An **independent audit** by multiple operators who check the robot's reasoning
3. A **circuit breaker** that automatically grounds the robot if anything looks wrong
4. A **permanent record** on the Juno blockchain that regulators, insurers, and courts can verify

And it does all this in **187 milliseconds** — fast enough that the robot doesn't have to wait.

## How It Works (Plain English)

Imagine you're managing a fleet of delivery robots. Each robot makes thousands of micro-decisions every second: how fast to go, when to brake, how close to get to a pedestrian.

Here's what JunoClaw does with each batch of those decisions:

### Step 1: Physics Simulation (1000 Hz)

The robot's controller runs its reflex loop 1000 times per second. Every single cycle, the physics engine snapshots the robot's complete state — wheel positions, speed, IMU readings, contact forces, distance to obstacles — and hashes it with SHA-256. Think of it as a **fingerprint of reality** that can't be faked after the fact.

After a batch of cycles (typically 1000), all those fingerprints get rolled into a **Merkle tree** — a cryptographic structure where one root hash proves the entire batch is intact. If anyone changes a single cycle's data, the root hash breaks.

### Step 2: Zero-Knowledge Proof (187 ms)

The robot generates a **128-byte mathematical proof** that its sensor readings stayed within the safety envelope — without revealing the actual sensor values. This is like proving you're over 18 without showing your ID. The proof is generated by one of five ZK circuits:

| Circuit | What It Proves | Time |
|---------|---------------|------|
| SensorSafety | Speed, force, distance, tilt all within limits | 80 ms |
| IntentConsistency | The robot's planned action is inside its operating zone | 119 ms |
| ConsensusMembership | A validator voted correctly (without revealing which one) | 51 ms |
| BatchSafety | An entire batch of reflex cycles in one proof | ~300 ms |
| Aggregation | All the above proofs agree with each other | 68 ms |

All five run in parallel: **187 ms total**. The proof is 128 bytes — smaller than a tweet.

### Step 3: Independent Audit (~300 ms)

The proof enters a **coordination network** — a mesh of 4+ nodes running Byzantine fault-tolerant consensus (same algorithm that secures billions in crypto assets). Before the network accepts the robot's decision:

1. **Proof-aware J-Lens gate**: Checks the ZK proof is valid. No proof? Auto-rejected. No further questions.
2. **Content audit**: If the proof is valid, the content of the decision is audited. Is the robot trying to do something deceptive? Multiple independent operators check.
3. **Truth Market**: Operators stake money on their verdicts. If they're wrong, they lose money. If they're right, they earn. This creates financial incentives for honest evaluation.
4. **Circuit breaker**: If any violation is detected, the robot's intent tier is **locked**. The robot enters safe-hold — reflexes keep running (physics doesn't stop), but it can't make new high-level decisions.

### Step 4: On-Chain Settlement (2.8 s)

The finalized, audited decision gets written to the **Juno blockchain** — permanently. Regulators can verify it. Insurers can price it. Courts can subpoena it. The on-chain verification takes 13 milliseconds.

### Step 5: Fleet Coordination

A **fleet coordinator** manages all the robots together:
- Aggregates intents from multiple robots into batches for consensus
- Rate-limits each robot (prevents a hacked robot from flooding the network)
- Routes circuit breaker trips back to the specific robot that violated
- Tracks fleet status: how many robots are operational, locked, or in safe-hold
- Exposes everything via REST API for dashboards and monitoring

## The Four Timescales

| Layer | Speed | What Happens |
|-------|-------|-------------|
| **Reflex** | 8-12 ms | Robot controls motors, reads sensors (hardware speed, no waiting) |
| **Proof** | 187 ms | ZK proof generated proving safety rules were followed |
| **Coordination** | ~300 ms | BFT consensus network audits and orders the decision |
| **Settlement** | 2.8 s | Decision permanently recorded on Juno blockchain |

**Proofs never gate physics.** The robot doesn't wait for the blockchain to brake. Proofs gate the *coordination layer* — the robot's ability to make its next high-level decision. If a robot violates safety, it gets grounded before it can plan its next move.

## The Physics Engine

The `junoclaw-physics` crate provides real physics simulation that produces cryptographic hashes from actual physics state — not hardcoded values.

Every reflex cycle (1 ms), the physics engine snapshots:
- Joint positions, velocities, and torques for each actuated joint
- IMU readings (accelerometer + gyroscope)
- Contact events (ground contact, obstacle collisions)
- Derived sensor readings: speed, max force, minimum distance to obstacles, tilt angle, acceleration magnitude
- Center of mass position and velocity
- Orientation (quaternion)

Each snapshot is **SHA-256 hashed** with canonical JSON serialization (sorted keys for determinism). After a batch of cycles, the hashes are rolled into a **Merkle tree** — one root hash proves the entire batch is intact. If anyone alters a single cycle, the root breaks.

The simulator models a differential-drive robot (like a TurtleBot or wheeled humanoid base) with:
- Gravity, ground contact, wheel friction
- Torque-to-force conversion with clamping
- Obstacle proximity sensing (raycast)
- Differential drive kinematics (independent left/right wheel control)
- IMU readings derived from actual dynamics (not random noise)

**35 tests** cover physics state hashing, simulator motion, turning, obstacle detection, contact events, IMU gravity readings, torque clamping, Merkle tree construction, proof verification, and full reflex batch attestation production.

## The Fleet Coordinator

The `FleetCoordinator` manages multiple robots as a group:

- **Registers/deregisters robots** — tracks which robots are in the fleet
- **Aggregates intents** — batches intents from multiple robots by time window (default 250 ms) for consensus
- **Rate-limits per robot** — prevents a single robot from flooding the network (default: 10 intents/second/robot)
- **Routes breaker actions** — when consensus detects a violation, the breaker trips for that specific robot
- **Tracks fleet status** — operational, locked, or in safe-hold — exposed via REST API
- **Auto-registers unknown robots** — if a breaker action comes in for an unregistered robot, it's tracked automatically

**14 tests** cover registration, breaker trip/reset, rate limiting, aggregation windows, fleet status, capacity limits, and deregistration.

## The Architecture (Simplified)

```
  ROBOT CONTROLLER
       |
  Physics loop (1000 Hz = every 1 ms)
  Each cycle: snapshot state → SHA-256 hash
       |
  Batch complete (1000 cycles)
  → Merkle tree of all cycle hashes → one root
  → ZK proof: "all sensor readings stayed within safety envelope" (187 ms)
       |
  FLEET COORDINATOR
  → Aggregates intents from multiple robots
  → Rate-limits per robot
  → Routes breaker trips back to specific robots
       |
  COORDINATION NETWORK (4-node BFT mesh, ~300 ms)
  → J-Lens gate: verify ZK proof → audit intent content
  → Truth Market: independent operators evaluate
  → Circuit breaker: trip if violation detected
  → REST API for relayers and dashboards
       |
  JUNO BLOCKCHAIN (2.8 s settlement)
  → zk-verifier: verify the proof on-chain (13 ms)
  → tee-attestation-verifier: verify TEE report
  → moultbook: permanent record
  → merkle-verifier: anchor the batch root
  → circuit-breaker: lock the robot
       |
  Robot is either cleared for next intent or grounded
```

## Post-Quantum Ready

JunoClaw is prepared for the quantum computing threat. Project Aegis implements hybrid post-quantum cryptography:

- **ML-DSA** (NIST-standardized lattice signatures) — 9 patches, gas benchmarked
- **MAYO** (NIST Level 5 post-quantum signatures) — streaming verification, 2.21× gas reduction with precompiles
- **SLH-DSA** (hash-based signatures) — hedge against all lattice attacks
- **Hybrid construction** — classical + post-quantum in every signature, so even if one breaks, the other holds

The Aegis forks (cosmos-sdk, cometbft, ibc-go) are built and tested. A 158 MB `junod-aegis` binary runs hybrid consensus. Rebase onto v31 once [#1223](https://github.com/CosmosContracts/juno/pull/1223) merges — v30 is live, v31 is in testnet prep.

### The Trust Wallet Gas Problem (and Why v31 Matters)

Right now, Trust Wallet users on Juno can't manually adjust gas fees. When gas prices spike, transactions silently fail. This affects every JunoClaw contract interaction from mobile wallets.

**v31 (PR [#1223](https://github.com/CosmosContracts/juno/pull/1223))** fixes this from two angles:
- **FeePay** — lets contract developers prepay user transaction fees. A JunoClaw fleet operator can fund a FeePay contract so robot operators don't worry about gas at all. v31 fixes denom overflow, sender-accounting bugs, and legacy contract-cap migration issues that blocked reliable FeePay usage.
- **Feemarket post-handler** — dynamic fee adjustment so transactions don't get stuck during congestion.

v31 is ready for testnet. Once it ships, JunoClaw fleet operators can use FeePay to make robot interactions gasless for end users — the fleet operator pays, the operator just sends the transaction.
