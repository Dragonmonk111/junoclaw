The substrate

JunoClaw is standing on the shoulders of giants.

Not a Cosmos SDK fork and not a Tendermint derivative. The agent layer was proven on Juno; the chain is built on Lay3r Labs’ layer-sdk and its slay3rd node; consensus runs on Commonware’s primitives; and execution is CosmWasm.

Juno

The agent layer was proven first on Juno testnet uni-7 — skill-registry, zk-verifier, jclaw-credential and moultbook still run there and on mainnet juno-1. The BN254 precompile came out of that work: ~203k gas per VerifyProof, a measured 1.823× cut, which is what makes verifying every task cheap instead of sampling.

Lay3r Labs

The chain descends from Lay3r Labs’ layer-sdk codebase and its slay3rd node. WAVS — Web Assembly Verifiable Services — is the runtime the agent layer uses to run work that can be checked rather than assumed.

Commonware

Consensus, broadcast and storage primitives beneath a Simplex-family BFT protocol. Equal-weight validators, deterministic finality, no staking at the consensus layer. The chain repo is layer-sdk on a commonware branch.

CosmWasm

Rust contracts on a deterministic KV store, with Cosmos-style gRPC — BroadcastTx, GetTx, Simulate — plus bank and wasm queries. Escrow, the task ledger, zk-verifier and the on-chain light client are all contracts.

The problem

Agents are about to do more work on chains than humans ever will.

They triage claims, verify credentials, settle disputes, route payments — and almost none of that runs on-chain, because chains are too slow and too expensive. Off-chain is where trust breaks: an agent in a laptop or a cloud VM can show you its answer, and you still have to take its word. “The AI decided” is the modern “the dog ate it.”

When the agent has a body, it gets worse. A dropped crate, a wrong dose, a blade at the wrong moment — that consequence doesn’t revert. So the proof has to bind before the machine acts, not after settlement.

How it works

Define, bound, fund, execute, verify, settle.

One loop, whether the agent is a model in a container or a machine on a factory floor. Every step leaves a receipt anyone can check.

01

Define

A soulbound agent identity: capabilities, model, reputation. Registered in agent-registry with a capabilities_hash and a running trust_score.

02

Bound

Constraint pre/post-hooks declare what this agent is permitted to attempt. A failing hook reverts atomically — nothing partially settles.

03

Fund

Escrow the reward non-custodially. The contract tracks the obligation; your wallet signs the transfer. It never holds your funds.

04

Execute

Local hardware, hired Akash GPU, or a robot in the field. Cross the compute boundary and the trust chain holds — the identity stays on-chain.

05

Verify

Four independent witnesses, not one: provenance, semantics, bounds, controllability. Read them ↓

06

Settle

Escrow releases on verified success and reputation ticks up; a bad result draws SlashAgent. The on-chain anchor outlives the payload.

Agents & DAOs

DAOs command agents. Agents form DAOs. Or a single agent, verified cryptographically.

JunoClaw is for verifiable agents and DAOs, and the two are bound together on-chain. Members of an agent-company are typed Agent | Human | SubDAO and weighted in basis points, with 51% quorum on ordinary proposals and 67% on constitutional ones.

DAO → agent

A DAO commands an agent

A DAO defines an agent, hires it, verifies its work, pays or slashes it. A WavsPush proposal carries the task, the execution tier and the escrow. A WeightChange proposal sets the roster — which agents are in, how much weight they carry. The DAO is the principal; the agent is the labour.

Agents → DAO

Agents form the DAO

A body whose members are agents, whose decisions are produced by verifiable computation rather than show-of-hands. truth-market runs verifiable outcome markets, moultbook is shared attestable agent memory, and sortition draws an arbitration panel from the members.

Single agent

Verified cryptographically

No DAO anywhere — one agent and one payer who wants the work verified. task-ledger accepts a task with no proposal_id, escrow records the obligation against a plain payer, and zk-verifier gates the release. This is the base case the other two are built on.

Verification is the base layer. A DAO is structure on top of it.

The four witnesses

Verification is not one proof. It is four independent ones.

An agent that controls a wallet or moves a machine is a small sovereign actor. “Trust the model” is not a governance answer, and neither is “trust whoever owns the server.” JunoClaw binds every consequential step to four witnesses.

WITNESS 01

TEE attestation

“Who ran what.” A signed measurement that a specific binary ran inside a specific enclave on specific silicon. This is a provenance statement.

● live
WITNESS 02

ZK proof

“Did it behave.” A Groth16 proof verified on-chain through the BN254 precompile — satisfying a declared predicate without revealing weights, prompts or private inputs. This is a semantics statement.

● live · ~203k gas
WITNESS 03

Constraint vocabulary

“What was it even allowed to attempt.” Audit-readable bounds attached to each task, evaluated around the Running → Completed transition.

● live on uni-7
WITNESS 04

Verifiable controllability

“Is the operator still meaningfully in control, observably from outside?” Compile-time hardening and runtime kill-switches, with a policy surface anyone can read.

● shipped

Why not just one? Witness 1 alone is provenance without semantics — proof the right server ran, zero proof it behaved. Witness 2 alone is semantics without provenance — proof that some valid trace exists, zero proof your enclave produced it. Bound together, an adversary must break a hardware root-of-trust and forge a proof against a circuit they do not hold the witness for.

AgentTrustAtLeastBalanceAtLeastPairReservesPositiveTaskStatusIsTimeAfterBlockHeightAtLeastEscrowObligationConfirmed

Seven constraints a task can refuse to be completed without. Deliberately an enum, not a callback: a reviewer reading AgentTrustAtLeast { agent_id: 42, min_score: 75 } knows exactly what will be checked.

Robotics

Verifiability for robots.

Every digital agent can fail backward: a bad swap reverts, a wrong verdict gets disputed, a payment is withheld. A robot cannot. So JunoClaw publishes what the machine was permitted to do, and proves it stayed inside that — before the actuator moves.

Locomotion and manipulation policies are trained in simulation, and the policy artifact is hashed and anchored on-chain — so the attestation ties the exact policy the robot shipped with to the actions it then took. Fleet operators keep compile-time hardening (dangerous code is not in the binary, so it cannot be reached) and runtime kill-switches (halt a capability in seconds, no redeploy, single-curl mean-time-to-halt). A planned read-only policy RPC lets anyone inspect which capabilities a fleet has armed before sending it work.

And an anchor outlives the payload: even when the telemetry stream is gone, the chain still holds “the robot reported X at time T, audited green.” For robotics liability, that is often the sentence that matters.

Proven, not promised

We broke it on purpose. Then we fixed what broke.

15

Chaos events in 24 h

Kill/restart, live network partitions, container recreates and a Byzantine proposer injecting faults. Victims rotated, and recovery was measured for every event.

0

State divergences

The monitor compared certified payload digests across validators, and those digests bind the Merkle state root itself.

3

Findings, all fixed

An IP-reassignment wedge and a backfill request flood. On top of that, app_hash now equals state_root, so it’s identical on every node.

2

Exploits caught on our own devnet

Our end-to-end probe reproduced a spoofed payment hook and an unbound marketplace verdict on deployed contracts. Both are fixed and migrated in place, and the probe now proves they fail.
