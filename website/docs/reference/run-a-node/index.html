Run a node

The JunoClaw node binary is slay3rd. It takes one argument: the path to a node.toml.

1. Get the binary

Section titled “1. Get the binary”

The chain source is on the commonware branch of Dragonmonk111/layer-sdk.

  • Build with Rust 1.97 or newer (the image uses rust:1.97-bookworm).
  • --features rocksdb gives the persistent store under data_dir. Without it, app state is not persisted across restarts.
  • On non-Unix hosts the binary verifies MAYO signatures but cannot produce them, so it cannot vote in hybrid mode.
  • Builds from before 2026-10-06 are incompatible. They stamp blocks with view-derived time, while the current set uses wall-clock time, so each side rejects the other’s proposals. Rebuild before rejoining.

For G1, accepted operators get a pinned commit and image digest so that every validator runs identical code.

2. Keys

Section titled “2. Keys”

Your keys.json holds:

  • BLS12-381 threshold share. Signs consensus votes
  • MAYO2 key (hybrid mode). The post-quantum half of every vote
  • Ed25519 identity. Authenticates your P2P connections

On devnet the coordinator generates keys centrally. Those shares come from a public seed, so the node only accepts them with insecure_devnet = true (see below). For G1, keys come out of the key ceremony: you generate your Ed25519 and MAYO2 keys locally, and the coordinator deals your BLS share from OS randomness and sends it to you encrypted (see Validators). Back up keys.json offline once. If you lose it, you lose your seat until the set is changed.

3. node.toml

Section titled “3. node.toml”

This mirrors the running devnet config:

Rules

  • validator_index must match the index your key share was generated for.
  • chain_id, the peer set and the binary version must be identical across the set. Mixed versions do not interoperate on P2P, so upgrades are all-or-none.
  • [[peers]] lists the other validators.
  • Clock. Your proposals carry your wall-clock time, and validators reject a block stamped more than 2 s ahead of their own clock. Run NTP (chrony or systemd-timesyncd).

insecure_devnet is for the devnet only. With it, the node accepts an empty genesis_path (the built-in devnet genesis), coordinator-dealt keys, and genesis files that fund or empower a built-in devnet address. Without it, the node refuses all three at startup. Never set it on G1.

5. Verify you’re participating

Section titled “5. Verify you’re participating”

Signs of a healthy node in the logs:

  • Heights should rise steadily. The single-host devnet finalizes about six blocks per second (0.16 s per block). A geographically distributed set will be slower.
  • app_hash should be identical across all validators at the same height. It equals the certified state_root.

Node up but not signing? Check that:

  1. validator_index matches your key share.
  2. Every peer is reachable on 7001, and their public keys are correct.
  3. chain_id and the binary version match the set.
  4. The clock is synced over NTP. If your clock is skewed by more than 2 s, peers refuse your proposals or you refuse theirs.
  5. If you just restarted after downtime: while the node is behind it logs verify: rejecting proposal / payload unavailable. That is expected. It backfills and then rejoins.

6. Operations

Section titled “6. Operations”
  • Pruning. pruning = "validator" (default) keeps the last 540,000 heights of sidecar data and finality records, about 24 hours at devnet speed. "rpc" keeps 16,200,000 heights (about 30 days) and "archive" keeps everything. Peers can backfill your node across that whole window. Beyond it, use state sync.
  • MAYO signature log. data_dir/mayo_sigs.log records the MAYO signature for every vote you cast. After a restart the node re-sends those exact signatures. A freshly signed vote would differ byte-for-byte, and peers treat that as a conflicting message. Keep the log with the data dir and never delete it while you are in the set.
  • Restarts. Nodes resume from persisted state. A node that falls far behind catches up with height-range backfill, or with certified state-sync if its data dir is empty.
  • Upgrades. Coordinated: everyone switches binary/config at an agreed height.
  • Incidents. Report in Telegram straight away: the height, the last log lines, and what changed.
